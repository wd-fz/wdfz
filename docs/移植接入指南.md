# 移植接入指南

## 1. 参考基线

旧版源码固定参考 [wd-fz/wd-fz.github.io @ `0bf508a`](https://github.com/wd-fz/wd-fz.github.io/tree/0bf508a47eac154c2a7047cdb45d314f61c48fdc)，这是归档前包含停止维护说明的 main。旧项目的产品对齐文档、模块清单、纯规则测试和历史验证记录可用于核对行为，但不是 Godot 版的完成证明。

移植先固定一个输入／状态变化和预期输出，再实现对应 Godot 规则与场景。JavaScript 文件不能直接改扩展名后交给 Godot；浏览器 API、Three.js、HTML、Canvas 音效和全局加载器都需要独立替换。

## 3. 接入一个功能模块

机房钥匙已按下面的流程接入，可作为后续独立物品／任务的参考：

1. 在 `features/keys/` 建立规则脚本，继承 `FeatureModule`，定义稳定 `keys.inventory` 模块 ID 和拾取交互 ID。
2. 实现 reset／capture／validate／restore。记录钥匙 ID 与数量，不能记录场景节点；重复拾取和满背包由规则判断。
3. 在 `GameApp._make_session()` 显式注册该模块并检查注册结果。跨模块依赖通过构造参数传入。
4. 创建一个 `WorldInteractable` 场景，设置 ID、提示文字、可见网格和碰撞层 2。让其在示例房间中可被射线命中。
5. 需要改变物品外观时，通过专用信号或视图适配器响应规则结果。读取存档重建外观，不能因此再发一次拾取命令。
6. 增加「首次拾取、重复拾取、失败拾取、读档后状态、新局清空、缺失模块默认值」的验证；运行 `python tools/check.py`。
7. 在计划索引更新状态，并在提交中写明旧版参考和未移植的行为。等垂直流程验证后再接正式校园。

简单模块参考 [DemoModule](../features/demo/demo_module.gd)；带依赖的流程参考 [InvestigationModule](../features/investigation/investigation_module.gd) 与 [InventoryModule](../features/inventory/inventory_module.gd)。加入新物品时先登记 `content/items/base_items.tres`，规则通过普通数据接收定义。源物品只有在成功入包后才标记领取；需要跨模块约束时实现无副作用的 `validate_snapshot()`。

## 4. 接入一个场景

1. 在 `scenes/worlds/` 创建根为 `Node3D` 的场景，不内置第二个玩家或主相机。
2. 地面与墙体放碰撞层 1，交互物层 2。使用真实物理体，不依赖网格名称推断碰撞。
3. 在 `content/worlds/` 创建 `WorldDefinition` 资源，配置唯一 ID、PackedScene、出生位置与日历策略。
4. 将资源加入 `app.tscn` 的 `WorldRouter.worlds`。开发阶段可修改 `GameApp.initial_world` 直接进入该场景。
5. 检查出生点、地面接触、墙体遮挡、窄通道、交互距离、读档、反复进入／退出。地图拓扑改变后，需要额外设计旧位置的恢复策略。

如果需要编辑器中单独预览房间，可临时添加预览相机；提交正式场景前移除或禁用，避免抢走玩家相机。

## 5. 规则迁移的验收方法

纯规则先验证固定输入，例如一次伤害、一次物品使用、一个阶段边界，不依赖画面。再检查与会话、UI、存档的连接，最后自然游玩完整流程。

时间相关功能至少区分：正常运行秒、暂停、正式过场、只冻结日历的区域、读档、跨日。不要重新引入「渲染每帧推进玩法」或「重新生成模型改变随机结果」。需要随机时注入玩法 RNG，并将确定结果／必要随机状态纳入模块存档；表现随机独立管理。

死亡、演出和预览的相机覆盖放在表现节点，退出时清理；角色位置与朝向由玩家适配器和会话交接管理。旧版曾经修复的生命周期问题要转成 Godot 回归，不能仅检查“看起来正常”。

## 6. 多人协作建议

可以分别认领规则、校园／导航、资源、UI／输入四条工作线。公共协议变更先在文档写清输入、输出和所有者；各自功能放独立目录，少改组合根。第一次集成选择一条小流程，集成通过后再扩充地图和异象。

本框架没有实现多人网络同步。后续若恢复联机计划，需要单独定义权威端、命令、快照、重连和作弊边界，不能把当前每局内存对象直接当成联机协议。
