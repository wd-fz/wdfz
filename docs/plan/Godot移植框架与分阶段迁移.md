# Godot移植框架与分阶段迁移

## 目标与基线

在 Godot 新仓库建立可运行、可测试、可分工的基础，再逐步迁移旧版的完整体验。旧仓库保留历史代码，新功能在 `wd-fz/wdfz` 开发。

技术基线为 Godot 4.6.3 标准版、GDScript、原生项目，初始框架使用 Compatibility，当前已统一为 Vulkan（桌面 Forward+、Android Mobile），见[渲染与验证](../渲染与Vulkan验证.md)。不同渲染器、导出平台和正式资源预算以实际设备测试决定，不在框架阶段承诺性能提升。

参考旧版 `0bf508a47eac154c2a7047cdb45d314f61c48fdc`。固定完整自然日 20 分钟作为迁移方向，保留“尽量首日通关、第二日起高危”的产品目标；框架示例没有实现正式难度曲线。

## M0：可运行的移植框架

交付项目入口、基础第一人称角色、测试房间、碰撞遮挡、键鼠与触屏输入、主菜单／暂停、每局会话、模块注册与交互协议、版本化存档和失效保护、自动验证、接入说明。

验收流程：启动 → 新局 → 移动 → 查看告示牌 → 暂停 → 保存 → 修改进度 → 读取 → 确认位置、视角、计时与模块状态恢复 → 返回菜单 → 新局清空。补充坏档、未知模块保留、多次进退、触屏输入释放及横竖屏验证。

阶段交付不含正式校园、游戏资产、异象和完整剧情。当前整体状态见本目录 README，验证事实见框架验证记录。

## M1：首条正式交互流程

迁移玩家状态、背包和物品定义，选择「调查线索 → 获取钥匙 → 开门」的小流程。先固定可复现的旧版行为样本，再实现规则、UI、存档和物件表现。

完成时应能在 Godot 中自然完成这条流程，并验证满背包、重复获取、无钥匙开门、读档、新局和失败提示。确定第一批稳定物品与场景 ID，禁止奖励由动画完成回调重复结算。

PR #2 当时的交付记录在[首条调查流程迁移与验证](../首条调查流程迁移与验证.md)；合并 PR #3 时该缩略切片已由正式校园移植取代。整体状态以本目录 README 为准。

## M2：正式校园与时间循环

迁移教学楼、走廊、楼梯及一条对外探索路径，建立尺寸、碰撞与导航的共同基线。接入正式开局时间、课表、学生会检查、外出许可、特殊时间窗口与跨日规则。

完成时验证一个完整 20 分钟自然日、连续探索、两个检查时刻、切场景、暂停／读档／跨日和日历冻结区域。物理与导航不随画质变化；正式模型迁移与基础几何验证分开进行。

## M3：生存压力与首条真结局

接入 SAN／违规／同化／体力、恢复与消耗、首日晚间升压、第二天高危、常驻巡察者、报警与核心异象。选择一条公开真结局完成端到端移植。

完成时自然游玩到通关，验证所有权、追踪、遮挡、离屏计时、危险预兆、失败与读档。画面和声音只反映规则，不生成第二份权威状态。

## M4：内容扩充与目标平台

逐项迁移其余公开路线、手机／网络终端、天赋、存档兼容、演出、音效与感官体验。进行 Windows／Linux 和 Android 的实际导出、输入、性能、听感及画面验收。

此阶段决定字体打包、资源预算、渲染器默认值、画质档位和发布方式。Web 导出若有需要单独评估，不能因为旧项目是网页就把它当成本轮默认交付。旧 Web 存档转换在稳定数据映射后再确定范围。

## M5：完整回归与交接

按功能清单逐项核对 Godot 与旧基线差异，区分保留、重新设计和暂未迁移。补齐自然完整路线、多天压力、重复死亡／新局、真实设备及长时间性能记录。

调试工具、成就、档案、速通、隐藏内容和多人联机分别确认范围；没有实现或没有验收的内容继续保留待办状态。发布前清理示例模块，保留可复现的自动验证和内容作者接入指南。

## 协作与依赖

M1 的规则与物品接口是 M2/M3 的前置依赖；美术与校园测量可以并行准备，但先提交一间房间供比例、碰撞和导入检查。M3 的首条通关路线通过后再大批量移植内容，减少系统边界反复修改。

每个功能提交注明旧版参考、实现范围、存档影响、验证方式和剩余缺口。公共接口以文档与可执行示例为准；临时的兼容适配必须写明删除条件。
