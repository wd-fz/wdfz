# 渲染性能分析与优化

基线为 main `053690f`。本次使用相同模型、画质、分辨率、机位和时间，分别测量原提交路径与优化路径；没有通过降低默认分辨率、删除场景物体或关掉阴影来形成对比。

## 为什么会浪费

1. **实例批次跨越整个楼层或校园。** 旧 Three.js 导出器按几何对象和材质的 UUID 分组，克隆的桌椅部件仍产生重复原型；每个 MultiMesh 又包含分散很远的全部实例。Godot 对一个 MultiMesh 整体剔除，不逐个剔除里面的实例。只要批次的大包围盒碰到视野或阴影视锥，就可能提交整批物体。默认教学楼有 1,657 个实例，室外有 10,117 个。
2. **合并大网格没有配套空间分块和遮挡剔除。** 以材质合并降低了绘制次数，却把墙、楼板和陈设的包围盒扩大到整层楼甚至整个校园。即使物体被墙挡住，提交和阴影投影仍有成本。基线教室固定视角约 50 万个三角形；关闭全部阴影后约 22 万个。此处计数是每帧渲染通道的提交量，包含重复阴影绘制，不等于场景中的独立三角形数量。
3. **隐藏入口预览仍完整实例化。** 进入房间会提前加载一整座室外校园；在室外会提前创建各入口背后的室内模型，之后才把远处预览隐藏。它们不一定每帧绘制，但占用资源、节点和加载时间。
4. **普通调色也要求屏幕 mipmap。** 屏幕后处理始终声明 `filter_linear_mipmap`，健康 SAN、无失焦时也要求引擎提供 mip 链。普通调色、扭曲、重影和光晕只用第 0 层，只有失焦模糊使用较高 LOD。
5. **相同同学材质各自创建。** 每个人都使用同样的颜色和光照模式，却有不同的材质资源，影响渲染器自动实例化。材质必须按 ClassmatesView 共享，不能与其他教室或死亡演出共用可变资源。

SSAO、辉光、多光源、软阴影和高档 MSAA 仍是明显的像素成本。诊断中关闭这些效果只用于归因，不是正式优化开关。固定画面测得的渲染提交 CPU 时间远低于 Vulkan GPU 时间；这不能推导出所有自然游玩场景都没有脚本或物理瓶颈。

## 实现与边界

- `CampusBatches` 以材质存储属性和原型顶点数据的 SHA-256 识别完全相同的原型，保留动态发光材质的语义名。按照空间和三角形预算递归分批，避免统一小网格产生大量空批次；保留每个实例的变换、颜色、图层和投影设置。
- `CampusMeshCells` 对超过 4,096 个三角形且跨越较大范围的不透明静态网格分块，顶点位置、法线、UV、切线和材质不变，为分块重新生成 LOD。缓存有数量上限；透明网格保留原深度排序分组。开放车库保留原批次，不套用没有收益的分块和遮挡。
- 遮挡网格只取实际不透明静态几何中的较大竖直三角形。门、电梯叶片、透明／镂空、面向镜头与渐隐材质不参与。物理墙高于真实墙面，并覆盖窗洞，因此不能把物理碰撞盒直接当作遮挡盒。
- 入口预览在 13 米内准备，继续使用原有 12 米显示、15 米隐藏阈值；最多保留两个已加载入口。重新加载时恢复门状态和电梯绑定，品质切换继续重建预览。楼梯、连廊和开放外廊仍按原连接关系显示。
- `ScenePost` 共用同一份 shader 主体，普通路径不生成 mipmap；需要失焦时切换 mip 路径，完整恢复已有 uniform。对未变的 uniform 不重复提交。没有删除原调色、低 SAN、黑闪或死亡反馈。
- 同学共享当前视图自己的材质，保留每个人的节点、运动、转头、起立、离校和显示状态。

原模型文件、碰撞、规则、存档、画质倍率、Vulkan 后端、Mobile 的 FXAA／辉光规避均保持原设定。遮挡与分批只影响表现层。

## 如何复测

```bash
# 需要真实窗口和 Vulkan。按顺序启动，防止窗口抢焦点影响采样。
python tools/benchmarks/render_profile.py --compare --samples 60
# 单独测移动渲染器和指定机位。
python tools/benchmarks/render_profile.py --compare --renderer mobile --scene out --scene teach1
# 单独归因屏幕后处理、SSAO、辉光、阴影、相邻预览、人物、灯光和分辨率。
python tools/benchmarks/render_profile.py --compare --renderer forward_plus --scene teach1 --ablate
```

默认保存到 `build/reports/render-profile/`：每个机位的截图、日志、完整 JSON 和 `summary.json`。输出包括实际驱动／渲染器／设备、固定机位、画质、样本数、平均／中位／P95 帧间隔、GPU 时间、渲染提交 CPU 时间、绘制次数和图元数量。比较模式在独立进程中关闭本次分批、分块、遮挡、预览延迟加载和材质共享，并使用原 mip 后处理路径；它是同一代码的受控比较，不声称复原基线中的所有非渲染行为。

性能采样使用真实 `frame_post_draw` 墙钟和 RenderingServer 时间戳，不传 `--fixed-fps`。固定逻辑、灯光时间、同学种子和机位；关闭调试碰撞线框。预热不计入样本，截图不计入帧耗时。GPU 指标可能有帧延迟，软件驱动与共享执行环境有噪声，应增大样本量并在目标设备多次复测。这里的 render CPU 时间不含整个游戏逻辑，不能当作整机 CPU 利用率。

## 验证记录

本机只有 Mesa llvmpipe 软件 Vulkan，没有硬件 GPU。测量使用 Godot 4.6.3、960×540、同档画质、VSync 关闭、四个软件光栅线程，分别运行 Forward+ 和 Mobile。相对结果用于定位多余提交和本环境中的回归，不能外推为 Android、Windows 独显或集显的实际 FPS。

测试覆盖实例变换／颜色守恒、静态三角形与顶点属性守恒、透明排序分组、可开关门洞的实际 Vulkan 像素、按需 mip 切换、入口缓存上限与门状态。原有走廊双面可通行检查、窗光、材质档位、旧版调色像素和同学动作对照继续保留。

每组预热至少 16 帧后采样 **32 帧**；以下是平均墙钟帧间隔，越低越好，采样期间新增管线编译均为 0。完整平均／中位／P95、GPU 与渲染 CPU 数据见[机器可读对照](渲染性能对照.json)。

| 路径 | 机位 | 原帧耗时 ms | 优化后 ms | 帧耗时减少 | 图元减少 | 绘制次数减少 |

| Forward+ | 教室 | 418.2 | 375.0 | 10.3% | 29.5% | 26.1% |
| Forward+ | 室外 | 434.3 | 302.2 | 30.4% | 66.8% | 18.7% |
| Forward+ | 网络中心 | 364.9 | 334.5 | 8.3% | 38.7% | 15.3% |
| Forward+ | 车库 | 318.6 | 306.4 | 3.8% | 0.0% | 0.4% |
| Mobile | 教室 | 870.8 | 829.6 | 4.7% | 29.5% | 29.5% |
| Mobile | 室外 | 385.3 | 265.9 | 31.0% | 66.8% | 16.1% |
| Mobile | 网络中心 | 499.2 | 306.0 | 38.7% | 38.7% | 15.1% |

车库的改善接近本环境波动，不视为已经解决其主要像素成本。分块与遮挡会增加部分 CPU 准备和剔除工作；本轮渲染提交 CPU 的中位时间增加约 0.1–0.4 ms，不能承诺所有硬件都得到同样比例的收益。首次分块准备、帧间波动和长局缓存占用仍需在目标设备测量。

八组固定机位的原生截图逐通道比较，平均差异均低于 0.001/255，单通道最大差异不超过 8/255；这只覆盖这些固定机位。旧 Web 调色的 13 组原生像素对照仍保持最大误差 1/255。

本次结构／工具检查、完整无窗口回归 **18,458 项**通过；Forward+ 和 Mobile 专项各 **374 项**通过，无脚本／资源错误。Linux 正式模板导出、X11 窗口启动与 PCK 资源／演出／开发工具烟测通过；这不是新 Release 发布。专项入口是 `tests/suites/render_optimization.gd` 及现有的 geometry、render_quality、grading、classroom_motion 套件。

后续仍需 Android 真机、实体 GPU 和自然长局验收。
